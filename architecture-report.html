Architecture Report

Forgefly runs its operations on agents, not headcount.

Forgefly is an AI-powered business OS for freelancers — client portal, proposals, invoicing, time tracking, and social promotion, generated from a single prompt and kept running by an AI copilot instead of a support team. The backend is a Deno/TypeScript edge-function layer (Supabase) that routes every judgment call — classify, draft, generate, decide — to Claude or OpenAI, while every deterministic task (read, write, charge, log) stays plain code against Postgres, row-level-security scoped to the signed-in business.

Architecture insights

What the code reveals

The security boundary is the actual product moat.

An LLM's output is only ever treated as data — a KPI catalog id, a recipient-selector mode, a caption string — never as query logic. It cannot name a table, a row, or a business id. Row-level security scoped to auth.uid() is the real enforcement layer; app-code discipline alone is never trusted to hold it.

Propose / execute, always two calls

Freeda's action bucket drafts a message and recipient list in one call; nothing sends until the user edits and explicitly confirms in a second, separate call.

Numbers are fetched, never computed

The KPI catalog match returns only an id — the frontend fetches the live value via the same code the Dashboard renders, so Freeda's answer can't drift from the screen.

Full-context stuffing over vector RAG

The documentation corpus grounding Freeda's support answers is injected whole into the system prompt — no embeddings pipeline, chosen deliberately for a corpus this size.

Model tiering by cost, not habit

Haiku handles classification and quick lookups; Sonnet is reserved for generation and grounded reasoning — a wrong number is worse than a slow one.

Two portal tables, easy to conflate

clients.status and contacts.lifecycle_status track similar-sounding but distinct lifecycles — a real source of a UI badge bug found and fixed this session.

Dead routes get found by tracing, not assuming

/dashboard/requests turned out to be a redirect stub; OnboardingPage.tsx looked dead but was still live-wired from two signup paths — both required reading the actual call sites.
