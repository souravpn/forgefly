## Decisions
- **Batch outreach uses sliding-window concurrency of 3**, not discrete "waves" — a rolling limiter handles cancel/add-mid-flight naturally, discrete waves don't. Chosen over simpler sequential processing for perceived speed (parallel Sonnet calls finish in ~1x time, not Nx).
- **No AI-invented named leads/companies.** Explored 3 lead-sourcing approaches (AI-generated names, curated directory, AI persona-brainstorm + user-supplied real companies) and rejected named-company generation outright — hallucination risk is unacceptable for cold outreach. Shipped: persona/archetype brainstorm (categories + where to search, no invented companies) + batch research on user-supplied real companies.
- **Kept both the old single-company wizard and the new batch/persona flow**, as two tabs in one page (`Research a Company` / `Research Outreach`), instead of replacing the old flow — user explicitly asked to preserve it after the initial rewrite removed it.
- **Image-generation for outreach visuals (discussed, not built):** confirmed use case is LinkedIn/portfolio assets, not inline email images (inline email images have deliverability/spam risk). Plan: Claude writes 2 image prompts from company intel + drafted copy, then OpenAI's image API (`gpt-image-1`, key already configured) generates the images — no new vendor needed. Not yet implemented; user was asked whether to build now or see test prompts first — no reply yet this session.

## Bugs / issues surfaced
1. **Invoice "Pay Invoice" email link went to bare `/portal` with no token.** Root cause: `InvoicesPage.tsx` called `generate-portal-link` with wrong params (`clientId`/`expiresInDays` instead of required `engagementId`); the function always 400'd and the error was silently swallowed. **Fixed**: added `resolveContactId`/`resolveEngagementId` helpers, call now passes proper `engagementId`, errors surface via toast instead of falling back to a broken link. Deployed & verified live.
2. **Portal Invoices tab showed "No invoices yet" despite a real invoice existing.** Root cause: invoices created via the normal form never set `contact_id` (column existed in DB, missing from the `Invoice` TS type and from `createInvoice`'s payload); portal query + RLS both require `contact_id IS NOT NULL`. **Fixed**: added `contact_id` to `Invoice` type, resolve it at invoice create/edit time, and backfill it on send/resend for pre-existing invoices. Verified live.
3. **Portal Projects tab showed nothing for a real linked project** — turned out **not a bug**: `client_visible_status` is an intentional per-project visibility toggle the freelancer sets manually; it was simply never set for that project.
4. **"Pay with Stripe" failed from the client portal** (network panel showed repeated `create-invoice-checkout` failures). Two stacked bugs: (a) the edge function required the *caller's own* session and filtered `invoices.user_id = caller.id` — but the caller from the portal is the client, not the freelancer, so it always failed; (b) even after fixing that, `ClientPortalPage.tsx` read `data.url` from the response when the function actually returns `data.data.url`. **Fixed both** — function now resolves access via `portalToken` → contact → business → owner chain when no freelancer session is present, and both portal call sites read the correct response path. Success/cancel redirects now route back into the portal. Deployed & verified live (real Stripe Checkout session opened correctly).
5. **User's explicit follow-on ask, addressed in the same fix**: a project attached to an invoice at creation time should auto-appear in the portal's Projects tab. **Fixed**: `ensureProjectVisible()` sets `client_visible_status` to `'in_progress'` when an invoice is created/edited with a `project_id`, and backfills it on resend for pre-existing invoices — only when the field was previously unset (never overrides a freelancer's explicit choice). Verified live.
6. **`ai-gateway`'s new `target_personas` mode initially returned empty results silently.** Root cause: `max_tokens: 900` was too low for PacUX's real (longer) niche/services combo, causing `stop_reason: "max_tokens"` mid-JSON truncation; the parse failure was swallowed and returned `personas: []` with no error surfaced. **Fixed**: raised to `max_tokens: 2000` and tightened the prompt to keep fields to one concise sentence each. Deployed & verified live.
