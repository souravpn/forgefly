## Decisions

- **Removed agency-tier gating repo-wide, but left the underlying capability intact rather than deleting it.** `isAgency` in `AuthContext.tsx` is untouched (just unused now); only the three call sites (`SocialPage.tsx`'s whole-page gate, `ClientsPage.tsx`'s team-member invite, `DashboardPage.tsx`'s promo banner) had their checks removed. This is explicitly temporary ("for now") per the user — re-enabling later is re-adding three `isAgency &&` checks, not rebuilding tier detection. Documented in `CLAUDE.md` and `src/components/promotions/CLAUDE.md` so a future session doesn't assume tier gating is enforced anywhere right now.
- **Public portal services fix: made the `services` table the single source of truth, rather than trying to keep two stores in sync.** Alternative considered: have `PackagesPage.tsx` also write back to `businesses.extracted_data.services` on every mutation, keeping `PublicPortfolioPage.tsx`'s existing JSONB read unchanged. Rejected — that's the same dual-write fragility that caused the bug in the first place (the AI/Freeda diff-apply flow already tries to keep the two in sync and clearly doesn't cover every write path). Instead, the public page now queries `services` directly, matching how the authenticated Services page already treats it as the real data.
- **Invoice numbering: atomic DB counter instead of a client-side retry-on-conflict loop.** A retry loop around the unique-constraint error would reduce collisions but not eliminate the race. Used a per-user/per-day counter table incremented via a single `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` statement, which Postgres guarantees is race-free (row lock held for the statement's duration) — removes the race window entirely rather than papering over it.

## Bugs / issues surfaced

- **Log Time widget and Market Research nav item invisible in production.** Root cause: the prior session's "market research engine" commit (`3288286`) was committed to local `main` but never pushed to `origin/main`, so Vercel (which auto-deploys from GitHub pushes, per `vercel.json`) never built it. **Fixed** — pushed; confirmed `origin/main` matches local `main`.
- **Services not showing on the public portfolio page (`/p/:slug`).** Root cause: `PublicPortfolioPage.tsx` read services from `businesses.extracted_data.services` (a JSONB snapshot populated only at onboarding), while the actual Services page (`PackagesPage.tsx`) writes real edits to a separate `services` table and never syncs them back to `extracted_data`. Any service added/edited/deleted after signup was invisible on the public page. Not an RLS problem on the query that was actually running — `businesses` already had a working public-read policy — but `services` itself had no public-read policy at all, which would have blocked the correct fix if attempted naively. **Fixed**: migration `00056_public_read_services.sql` (public SELECT policy on `services`, scoped to active businesses) + `PublicPortfolioPage.tsx` now queries `services` directly. Pushed to prod, RLS policy confirmed live via direct query.
- **Invoice creation failing: "duplicate key value violates unique constraint invoices_invoice_number_key".** Root cause: `generateInvoiceNumber()` in `invoiceService.ts` did `SELECT count(*)` of today's invoices then inserted with `count + 1` as the sequence — not atomic, so two near-simultaneous creates could read the same count and collide. Confirmed via prod query that today's invoices were `001`/`002` with no gaps, consistent with a genuine concurrent-request race rather than stale data. **Fixed**: migration `00057_atomic_invoice_numbers.sql` (an `invoice_number_counters` table + `next_invoice_sequence()` RPC using atomic `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`), with a backfill step seeding each user's counter from their current max invoice number so nothing collided immediately post-migration. `invoiceService.ts` rewritten to call the RPC. Pushed to prod; backfilled counter confirmed correct for the affected user (`55cf9c59-5ab9-402e-add0-f8f9217c306d`, counter seeded to 2, matching existing `001`/`002`).
