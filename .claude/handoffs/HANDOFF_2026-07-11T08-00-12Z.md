## Session goal

End-to-end test the Instagram/WhatsApp integration (forgeflydev Meta app) built in prior sessions — both platforms' connect flows, inbound/outbound WhatsApp messaging, and the three automated lifecycle notifications (proposal approved, invoice paid, file shared) — fixing whatever broke along the way, then extend to real two-way WhatsApp send and polish the surrounding UI (Connections grid, Settings public-identity fields, phone number entry).

## Decisions

- **Kept the existing `forgeflydev` Meta app** rather than registering a new one; user manually deleted stray duplicate apps from their own Meta developer account instead.
- **Consolidated the OAuth redirect_uri from `/settings?tab=account` to `/dashboard/social`**, moving the OAuth-completion effect out of `SettingsPage.tsx` into `SocialPage.tsx`, since the Connect UI already lives there and the Settings bounce was leftover cruft. User re-registered both Instagram Login and Facebook Login redirect URIs in Meta's dashboard to match.
- **`sendWhatsapp()` takes an optional `clientId`** and threads it through `messages.client_id` on every insert, resolved via `resolveContactIdByPhone()` when the caller only has a `clients.id` (invoice/payment flows) rather than a `contacts.id`. Chosen over app-wide phone-format normalization — linking by `client_id` fixes "Unknown number" thread fragmentation regardless of phone format inconsistency.
- **Real two-way WhatsApp send is heuristic-gated**: the dashboard's reply box (`MessagesPage.tsx`) only dispatches via WhatsApp (new `send-whatsapp-message` edge function) when the selected contact's thread already contains a `channel: 'whatsapp'` message, WhatsApp is connected, and the contact has a phone — otherwise it still logs a portal-only message. Chosen over "always send WhatsApp if a phone is on file" to avoid surprising portal-only clients.
- **Every first-time inbound WhatsApp message from an unrecognized number auto-creates a Prospect lead** (contact + `pipeline_leads` row, `service_name: 'via WhatsApp'`) directly in `whatsapp-webhook`, rather than requiring the freelancer to manually save it. The manual button ("Save this Lead as Client") still exists as a fallback — it now navigates to `/dashboard/leads?action=new&phone=...` and opens the New Lead modal pre-filled, rather than using its own inline dialog.
- **Built a reusable `PhoneInputField` component** (`react-phone-number-input`, country-flag dropdown + dial code) and swapped it into every phone entry point that feeds the WhatsApp system (Settings contact phone, Leads new-client phone, Clients phone) so all *new* numbers are captured in proper E.164 format. Explicitly **not** applied retroactively to existing data, and **not yet** applied to the Client Portal's own "Complete your profile" phone field (different `--p-*` theming system — flagged, not done).
- **`messages.sender_id` made nullable via migration** instead of inventing a synthetic system user — WhatsApp-originated messages (inbound from a non-authenticated contact, outbound from automated events) have no real `auth.users` row behind them.

## Bugs / issues surfaced

All of the following are **fixed and deployed** unless marked otherwise:

- `VITE_INSTAGRAM_APP_ID` / `VITE_META_APP_ID` missing from Vercel Production/Preview env → prod builds baked in `client_id=undefined`. Fixed: added to Vercel, redeployed.
- OAuth redirect_uri pointed at a route (`/settings?tab=account`) that never existed → router's catch-all swallowed `code`/`state`. Fixed via the redirect consolidation above.
- OAuth-completion effect could fire twice, racing two exchanges against the same single-use authorization code. Fixed with an `oauthHandledRef` guard.
- `messages.sender_id` NOT NULL silently killed every WhatsApp-channel insert (inbound webhook + outbound `sendWhatsapp`), with no error surfaced. Fixed via migration `00042` + added `console.error` on both insert paths.
- `ProposalsPage.tsx`'s plain "Create Proposal" path never set `user_id` (NOT NULL FK) and never checked the insert error → silently failed while showing a false success toast. Fixed.
- `sendWhatsapp()` never set `client_id` → every outbound notification landed as an orphaned "Unknown number" thread. Fixed via `resolveContactIdByPhone()` + `clientId` param threaded through all callers.
- **Meta account checkpoint** (`OAuthException` code 190 / `error_subcode 459`) blocked all outbound sends and likely also inbound webhook delivery. **Fixed by user action** — cleared via facebook.com, then Disconnect/reconnect WhatsApp in Forgefly for a fresh token. Confirmed working: fresh token tested directly against Graph API, inbound message received successfully afterward.
- Invoice-paid client-side notification failed for one test contact: `clients.phone` stored without a country code vs. `contacts.phone`'s `+1...` for the same person. **Open as a systemic concern for old data** — now mitigated going forward by the new `PhoneInputField` (E.164 enforcement on new entries), but old rows are untouched.
- Dashboard's manual reply box (`MessagesPage.tsx`) never sent via WhatsApp at all, only ever logged `channel: 'portal'`. Fixed — new `send-whatsapp-message` edge function + thread-detection heuristic.
- **`whatsappConnected` state always false in `MessagesPage.tsx`** — it queried the `social_connections` table directly from the browser, but that table has RLS enabled with **zero policies defined** (default-deny for anything but service_role, since it holds access tokens). Fixed: now reuses the same `getSocialConnections()` service call (backed by the `get-social-status` edge function) that the Social page already uses correctly.
- **Session-window check used exact string match on `wa_phone`** (`+14086368006` vs. the actually-stored `14086368006` for the same person) → always concluded "no reply in 24h" and sent Meta's generic `hello_world` template instead of the freeform typed text, even when the client had replied minutes earlier. Fixed: now matches by `client_id` when known, falling back to phone-normalization only when there's no linked contact. Redeployed to all 5 functions sharing `whatsappSend.ts`.
- Note the `hello_world` template itself is a fixed Meta boilerplate with no variable placeholders — even with the session-window bug fixed, a reply outside the 24h window will never carry custom text; only a real Meta-approved template with body variables could do that, and none is registered yet.
