## Decisions

- **Phased Social build**: Phase A (AI captions + competitor tracking) shipped with zero Meta dependency first; Phase B (real Instagram publish + WhatsApp outbound send) came once Sourav had a working Meta Developer App. Alternative was building full integration in one pass — rejected because Meta App setup takes days/weeks and blocking all Social features on that was wasteful.
- **Credentials in `social_connections`, no Connect UI yet**: new service-role-only table (no client-side RLS SELECT — tokens never reach the browser), populated via manual SQL insert for the single test account (`PacUX`, business_id `4ab15116-00aa-4d66-a554-6165f7d31565`). Building a real OAuth Connect UI was explicitly deferred — only one account needs this right now, building UI for it is premature. **User confirmed twice this is the immediate next-phase priority.**
- **Competitor handle discovery is search-grounded, not LLM-recalled**: reuses `research-company`'s fetch-search-results-and-regex-extract pattern. Exact @handles are exactly the kind of narrow fact LLMs hallucinate, so handles only ever come from real search-result text, never model memory.
- **Instagram identifies the account via literal `me` in the URL path**, not the numeric Instagram User ID shown in the Meta dashboard. The numeric ID is not a valid graph node for the newer "Instagram API with Instagram Login" product (unlike the older Facebook-Page-linked flow). Found via systematic curl isolation testing.
- **Instagram publish polls container `status_code` until `FINISHED`** before calling `media_publish`. Immediate publish-after-create races Instagram's async server-side image processing and throws `"Media ID is not available"`.
- **Access token sent via `Authorization: Bearer` header, not JSON body param** for Instagram Graph calls — body-param tokens weren't recognized, producing a misleading generic "object does not exist / missing permissions" error.
- **WhatsApp scope this pass = outbound send only.** Inbound webhook, `messages.channel` column, session-vs-template branching, and wiring proposal-approve/invoice-pay/file-send through WhatsApp are all deferred — nothing inbound has been proven yet, and it's a much bigger build. **User confirmed this is also an immediate next-phase priority.**
- **Landing-page 3-tier pricing (Solo/Pro/Agency) stays decoupled from the real Stripe-wired `UpgradeModal` pricing** ($29/mo agency). Only touched marketing copy — the two were already disconnected before this session and the user only asked for "UI changes," not billing changes.
- **Extracted `SiteHeader`/`SiteFooter` into `src/components/marketing/`**, shared across Landing/Contact/Documentation. Avoids ~500 lines of duplicated nav/footer JSX across three files.
- **Documentation moved from protected `/dashboard/documentation` to public `/documentation`**, now uses the same shared header/footer as Contact for visual consistency (not explicitly requested, reasonable default since it's now a public top-level page).
- **Contact page "Send message" wired to `mailto:`**, not a real backend — no contact-form edge function exists and building one wasn't requested; kept the same honest pattern the original ContactPage already used.

## Bugs / issues surfaced

- **Instagram publish "Object does not exist" error** — three stacked root causes, all fixed: (1) initial OAuth consent didn't include the publish scope (fixed by disconnecting/reconnecting the Instagram Tester role and re-granting with "Access and publish content" toggled on), (2) token sent as JSON body param instead of `Authorization: Bearer` header (fixed), (3) used numeric Instagram User ID instead of literal `me` (fixed). Status: **fixed**, real post successfully published to the `forgeflydev` test account.
- **Instagram `media_publish` race condition** — `"Media ID is not available"` from calling publish immediately after container creation, before Instagram finished processing the image. Status: **fixed** via polling `status_code` (up to 15 attempts, 2s apart) until `FINISHED`.
- **Duplicate Instagram post on `forgeflydev`** — a manual debugging curl call to `media_publish` actually published a real post outside Forgefly's DB tracking, so the app's own re-publish guard (blocks once `status='published'`) never saw it, and a later legitimate UI click published it again. Status: **open** — needs manual deletion on Instagram itself, not fixable from Forgefly (no delete call was made).
- **Instagram/WhatsApp access tokens were exposed in plaintext multiple times** during debugging (screenshots + full curl commands pasted in chat). User was told to regenerate after each exposure — **verify tokens currently in `social_connections` are post-regeneration before trusting them.**
- **"Manage plan" button in Settings > Account > Billing and Subscription doesn't open `UpgradeModal`.** Extensively debugged and ruled out: wrong click target, stale Vite HMR, missing onClick wiring, thrown JS errors (none), Dialog portal not mounting even via direct React prop invocation bypassing the click entirely. Proven **not specific to new code** — an untouched pre-existing dialog (`ClientsPage` "Add Team Member") fails identically in the same session, including in a brand-new tab. Root cause unknown, suspected Vite dev server environmental state after a very long single session of continuous HMR. Status: **open, explicitly parked** per user request. Untested fix: restart the dev server.
- **`npx supabase functions` (CLI v2.109.0) has no `invoke` subcommand** — testing edge functions from the terminal isn't possible with this CLI version; used browser DevTools console (`supabase.functions.invoke`) or curl with a manually-extracted session token instead.
- **Remote migration history was out of sync early in session** — tracking table showed zero migrations applied even though 36 were genuinely live. Fixed via `supabase migration repair --status applied` for 00001–00036, after verifying real schema state with direct PostgREST table-existence probes (never trust the tracking table blindly — check actual schema state first).
